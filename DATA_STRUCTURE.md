# DATA_STRUCTURE.md

## Overall Structure

```text
Google Spreadsheet (per user)
│
├── Settings
├── ReminderItems      ← main application data
└── Logs
```

`Users` (a cross-user table) is **not** stored inside a per-user Sheet — it
would break isolation. The mapping of "which email owns which Sheet ID"
lives centrally, outside any individual user's Sheet: Apps Script's own
Script Properties store, keyed `SHEET_ID_<email>` (see ADR-010).

## 4.1 Sheet Definitions

### Sheet: `ReminderItems`

**Purpose:** the core data — every Fixed Deposit, school fee, or other
renewal item the user is tracking.

Reminder items use a generic structure with a `Category` field, rather
than separate hardcoded sheets per type — so Insurance, License, or other
future categories can be added later without a schema change.

| Column | Type | Required | Description |
|---|---|---|---|
| ID | String | Yes | Unique record ID (e.g. UUID) |
| Category | String | Yes | `FixedDeposit`, `SchoolFee`, `Insurance`, `License`, `Subscription`, `Other` — see 4.2 |
| Title | String | Yes | User-facing name, e.g. "Maybank FD - Emma" |
| DueDate | Date | Yes | Next date this item needs action |
| RecurrenceInterval | String | No | e.g. `Monthly`, `Yearly`, `None` — used by "Mark as Renewed" (FR-008) |
| Amount | Number | No | Optional amount (deposit sum, fee amount) |
| Notes | String | No | Free text |
| IsDone | Boolean | Yes | Whether this item is completed (one-off items only) — see 4.2 |
| CreatedDate | DateTime | Yes | Creation timestamp |
| UpdatedDate | DateTime | Yes | Last update timestamp |

Additional fields beyond this are `TBD` — not invented ahead of real need.

### Sheet: `Settings`

**Purpose:** per-user app preferences.

Content: `TBD` (no confirmed settings yet — placeholder tab created at
Sheet-initialization time so the structure exists when needed).

### Sheet: `Logs`

**Purpose:** lightweight record of write actions (create/update/delete)
for troubleshooting — not a full audit system.

| Column | Type | Required | Description |
|---|---|---|---|
| Timestamp | DateTime | Yes | When the action happened |
| Action | String | Yes | `Create` / `Update` / `Delete` |
| ItemID | String | Yes | Which `ReminderItems` row was affected |
| Result | String | Yes | `Success` / `Error` |

## 4.2 Data Rules

- **Unique IDs:** generated by Apps Script at creation time (not
  user-supplied), guaranteed unique within a user's own Sheet.
- **Date format:** ISO `YYYY-MM-DD` for all dates, stored and transmitted
  consistently (timezone handling: `TBD`).
- **Required fields:** enforced both in the frontend form and again in
  Apps Script before any write.
- **Optional fields:** may be blank; blank is stored as an empty cell, not
  a placeholder string like `"N/A"`.
- **Status is a calculated display value, not stored data.** Only
  `IsDone` is stored (true/false). The display bucket (`Overdue` / `Today`
  / `ThisWeek` / `NextWeek` / `ThisMonth` / `Later` — ADR-015) is computed
  on read — every time the app loads — by comparing today's date to
  `DueDate` as a rolling day-count from today. This avoids the stored
  value ever going stale relative to the real due date. A recurring item's `IsDone` is
  irrelevant to its display grouping — completing a renewal just advances
  `DueDate` and the display recalculates from there.
- **Duplicate handling:** no automatic duplicate detection in Phase 1 —
  the user is responsible for not entering the same item twice.
- **Validation:** `DueDate` must be a valid date; `Category` must be one of
  the recognized values (see 4.1 — `FixedDeposit`, `SchoolFee`,
  `Insurance`, `License`, `Subscription`, `Other`); `Amount`, if present,
  must be numeric and non-negative.

## 4.3 User Data Isolation

Every `ReminderItems`, `Settings`, and `Logs` sheet lives inside a
Spreadsheet file that belongs to exactly one authenticated user. Apps
Script resolves "which Spreadsheet" purely from the verified caller
identity (see ARCHITECTURE.md 3.2) — there is no `UserID` column inside
`ReminderItems` because isolation happens at the *file* level, not by
filtering rows within a shared file. This means a bug in row-filtering
logic can never leak another user's data, because another user's rows are
never in the same file to begin with.
